# Repository instructions

## Context by task

- Before implementation, read the [common backend conventions](https://github.com/pipesor-org/pipesor-docs/blob/main/docs/development/backend-conventions.md). Use the accessible pipesor-docs checkout when available, distinguishing local changes from integrated main. Apply only the conventions relevant to this service; they do not add tables, integrations or permissions.
- Use [README.md](README.md#development-and-verification) for setup, runnable commands and contribution policies. Add verified commands there when introducing application tooling; reference them rather than maintaining a second command list here.
- For retrieval behavior, corpus eligibility or provenance changes, consult [architecture](docs/architecture.md) and its current knowledge-scope model and invariants. Read ADR-015 for the boundary with diagnosis orchestration and ADR-019 for the managed AI foundation. Follow references for the affected subject, not the entire documentation set for every edit.
- For Python dependency selection, vector compatibility, persistence or delivery work, consult the relevant sections of the [deployment contract](docs/deployment-contract.md). Its development baseline records the authorized version-selection policy; its configuration and data sections identify embedding, corpus and ownership requirements.
- Treat local architecture summaries as navigation, not frozen specifications. Use the accessible `../../pipesor-docs/` checkout or linked sources on `main`, accounting for later accepted decisions and relevant uncommitted changes. Inspect uncommitted source changes separately; their presence does not establish integration or approval. Report unavailable or conflicting evidence when it affects the task. Documentation links must follow `main` across repositories and relative paths within this repository; a consulted revision may be recorded as text only.

## Implementation constraints

- Retrieve only authorized knowledge within the documented scope and preserve document/chunk provenance in results. Semantic similarity, possession of a document ID or caller access to this service does not establish authorization to every source. Keep sensitive or unauthorized content out of responses and diagnostic logs.
- Keep evaluation cases and reference solutions out of the retrieval corpus and corpus-loading fixtures that could contaminate evaluation. Real corpus eligibility requires authorization and provenance evidence; reviewed incidents are eligible only within those boundaries, not automatically because a diagnosis exists.
- Confine writes to owned knowledge tables and preserve document/chunk relationships. Shared PostgreSQL infrastructure does not authorize writes to operational evidence or diagnoses, cross-schema foreign keys or cross-context ORM navigation. Ownership does not approve a corpus ingestion/update mechanism; do not add crawlers, automatic learning from diagnoses or loading jobs while that mechanism remains undecided.
- Check embedding compatibility across query vectors, stored chunks, schema and indexes. Do not infer model, dimension, re-embedding or migration behavior from the provider or Foundry account/project. The foundation does not establish a compatible application endpoint/SDK or authorize an undeclared direct provider call.
- Keep the synchronous retrieval contract with recommendation_service. Do not add diagnosis generation, LLM orchestration, model training, a new vector database or a public business API to complete retrieval. Component projections do not create additional callers or deployments. No-match results and retrieval failures must remain distinguishable under the agreed API contract; do not fabricate supporting knowledge.
- Verify FastAPI, PostgreSQL/pgvector client and transitive dependency compatibility together against the authorized Python baseline in an isolated project environment. Report incompatibilities rather than silently replacing the runtime or storage technology.
- A request to implement a local increment authorizes its required local code, tooling and checks. Do not create cloud resources, permissions or secrets, or modify neighboring repositories as a side effect. Keep credentials and sensitive evidence out of committed files and reported output.
- If model/dimension (PD-005), corpus loading/update (PD-006), eligible corpus evidence (PD-023) or a required API/access contract is unresolved, identify its impact on the increment. Continue independent scaffolding and isolated tests; do not invent the missing agreement or block the whole service over unrelated decisions.

## Verification and handoff

Use the applicable checks documented in the README. Add behavior checks with the first executable increment, including material cases for unauthorized sources, evaluation leakage, preserved provenance, incompatible vectors, no matches and failed retrieval. Use synthetic documents, isolated fixtures and mocked remote integrations; passing such tests is not evidence of real corpus eligibility or provider compatibility. Live database or provider checks need their own agreed scope and access.

For documentation-only edits, check affected links and source coherence; parse TOML when changing agent configuration. Do not claim a build or integration passed before it exists and has run. Keep the documentation that owns a changed behavior or command current in the same change. Report what changed, checks actually performed and remaining blockers. For substantial work spanning sessions, keep a task-specific plan with scope, acceptance criteria and verification progress; a small edit needs no plan file.

When a focused review is warranted and delegation is authorized, `rag_reviewer` checks corpus authorization, evaluation separation, provenance, knowledge ownership and vector compatibility. Supply the task and affected paths. Its review supplements the main agent's verification and human review.
